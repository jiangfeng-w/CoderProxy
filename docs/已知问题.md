> 以下 §1–§8 为**修复前**的问题记录（现象/根因/证据对照的是 2026-09-24 归档补丁半成品与 main 裸奔态），保留作排查历史；其中 §6 建议方向与 §7 验收清单**已按上表实现/满足**。

### 1. 背景

牛码网关间歇性返回 HTTP 200 后立即干净关流（0 token 空流），日志诊断 kimi-k3 56% / glm-5.3-flash 86% 的 `chat_done` 为空响应。此前 relay 如实转发成「成功但空」，TRAE 客户端靠自身重试掩盖，ZCode/CodeBuddy 直接报错。

正在做的防御意图：relay 内对空响应自动重发上游请求（`RELAY_EMPTY_STREAM_RETRIES`，默认 3）；耗尽仍空则抛错，由 `gen()` 记 `chat_error`——**不再向 agent 发假成功的空流/空 JSON**。该意图在非流式（`chat_with_empty_retry`，`range(max_retries + 1)` 计数正确）侧成立；**流式侧未达成**。

### 2. 现象

流式请求遇持续空流时（默认 `empty_stream_retries=3`）：

- 上游只被调用 **2 次**（期望 1 + 3 = 4 次），重试预算被硬顶成 1 次；
- 耗尽后生成器**正常结束、不抛错**，`gen()` 于是记成 **`chat_done`**（正是本次改动要消灭的「0 token 假成功」，只是从「空流」换成「截断流」）；
- 客户端收到：**HTTP 200**、**2 个 role 帧**、**无 `finish_reason` 帧**、**无 `[DONE]`**——既不报错也不收尾，比原空流更难排查。实测帧序列：
  ```
  ["chunk(role='assistant', finish=None)", "chunk(role='assistant', finish=None)"]
  ```

### 3. 根因（4 处，集中在同一条循环）

| # | 位置 | 问题 |
|---|---|---|
| 1 | `routes.py:223` `for attempt in range(2)` | 空响应重试与既有 401「刷新目录后重试一次」**共用一个循环和同一个 `attempt`**，两个独立预算互相挤占 |
| 2 | `routes.py:233-237` 空响应分支 | 条件满足时 `continue`；`range(2)` 迭代完即落到循环外，**无终局 `raise`** → 生成器正常结束 |
| 3 | `oai_adapter.py:382` + docstring（`routes.py:216`） | docstring 称「重试只发生在预拉首帧之前，首帧缓冲保证响应头未发」，但 `stream_openai_sse` **无条件先 yield 一个 role 帧**，预拉 `anext` 必然成功 → 响应头已发，**前提不成立**。故 `retries=0/1` 也只能「HTTP 200 + 流尾补错误帧」，**无法像 401/403 那样透传真状态码**；且每重试一次多吐一个 role 帧 |
| 4 | `oai_adapter.py:85-94` `_raw_tail_desc` | `raw_tail`（上游原始 SSE 行）被写进**面向 agent 的错误消息**。实测错误帧含 `upstream_raw_tail=["data: {\"type\":\"message_stop\"}"]` 等 **Anthropic 原生行**——触碰 `AGENTS.md` 硬性规则 2「禁止把 ta3/Anthropic 内部泄漏给 agent」 |

### 4. 证据（keyless，均不触发牛码网络）

- **持续空流**（默认 `retries=3`）：HTTP 200 / 上游调用 2 次 / 落库 `chat_request, chat_done` / 2 个 role 帧、无 `[DONE]`。
- **重试档位枚举**（持续空流）：`retries=0` → 抛错（记 `chat_error`）；`retries=1` → 抛错；`retries=2/3/5` → **正常结束不抛错**（`retries>=2` 即坏，**含出厂默认 3**）。
- **第 3 次才成功**：`retries=3`、上游序列「空, 空, 成功」→ 上游只调 2 次，**客户端拿不到本该在第 3 次返回的内容**。
- **401 路径现状（须保持）**：上游序列「401, 成功」→ 上游调用 2 次、目录同步 1 次、落库 `chat_request, auth_401_refresh, chat_done`、客户端拿到内容 ✓。
- **「最小改法」不安全**：曾拟把上界改为 `empty_retries + 1`，控制流对照实验显示：`retries=0` 时该改动使 **401 刷新路径掉出循环（`FELL-OFF`）**，即会**回归既有 401 刷新能力**。**该方案已否决，勿按此改。**

### 5. 为什么 171 个测试全绿

`tests/test_empty_stream.py` 的新用例恰好避开了坏组合：

- `test_sse_with_retry_empty_then_success`：`retries=3` 但**第 2 次就成功**，走不到耗尽；
- `test_sse_with_retry_empty_exhausted_raises`：用 `retries=1`，而该档位恰好正确。

**默认档（3）下的「耗尽」路径无任何用例覆盖。**

### 6. 建议修复方向（待定稿，未实施）

1. **拆分预算**：空响应重试独立计数（`empty_stream_retries`），401 刷新重试保留自己的单次配额，不共用同一 `for`/`attempt`。
2. **耗尽必抛**：循环结构保证「要么 return 成功、要么 raise」（如 `for...else: raise` 或显式终局判断），不留 fall-through。
3. **判定先于产出**：把空响应判定前移到**任何帧 yield 之前**（先缓冲上游事件直至可判定「非空」再释放，含 role 帧）。这样空响应时响应头未发，`routes` 才能像 401/403 一样**透传真状态码**；非空时才开流，同时消除重试重发 role 帧。
4. **`raw_tail` 只进日志**：内部诊断留在 `logger` / `chat_error` 落库 detail，**不进**面向 agent 的错误消息（合规：硬性规则 2）。

### 7. 验收（修复后须补的回归用例）

- 默认档（3）持续空流：**必须 raise**，落库 `chat_error`（非 `chat_done`）；→ 已满足（`test_sse_with_retry_empty_exhausted_raises_all_tiers[3]`、`test_endpoint_stream_empty_502_not_fake_success`）
- 上游「空, 空, 成功」：客户端**必须拿到第 3 次的内容**；→ 已满足（`test_sse_with_retry_empty_then_success`、`test_endpoint_stream_empty_then_success_delivers_content`）
- 401 刷新路径（`retries=0` 与 `=3`）：**不得回归**（仍能刷新目录后重试成功）；→ 已满足（`test_sse_with_retry_401_still_works_with_empty_retries`、`test_endpoint_401_refresh_end_to_end`）
- 面向 agent 的错误体**不得含 Anthropic 原生行**（如 `message_stop` / `message_start`）。→ 已满足（`test_endpoint_stream_empty_502_not_fake_success` 的合规断言；raw_tail 只进日志 detail）

### 8. 复现方法

`relay/tests/` 内已有 keyless 假 provider 基建（`_FakeStreamProvider` 等）。复现要点：构造持续返回空 done 事件（`usage=Usage()` 全 0、`tool_calls=[]`、`raw_tail` 非空）的假 provider，经 `routes._sse_with_retry` 或 `/v1/chat/completions`（`stream=true`）观察「上游调用次数 / 帧序列 / 落库 kind」，逐档位对比 `empty_stream_retries`。

> 注（历史）：修复前 `empty_stream_retries >= 2` 即触发坏路径，默认 3 故默认即命中；修复后各档位行为见 `relay/tests/test_empty_stream.py` 的参数化用例。

## BUG-002 responses 并行工具调用顺序断裂致上游 400 code=11148（**已修复 2026-10-09**）

> 状态：**已修复**（2026-10-09，四 bug 会话首批；根因与复现由上一轮会话实证，修复见下方「修复记录」）
> 位置（修复前）：`relay/relay/protocol_adapter.py::responses_to_chat_request`（`function_call` / `function_call_output` 两分支的 flush 时序）
> 影响等级：高。**顶死整条会话**——坏历史被每次请求原样重放，上游对之后每条消息都返 400。

### 1. 现象

ZCode 用 `WorkBuddy/deepseek-v4.1-flash` 等模型带工具多轮时，上游返回
`tool calls and tool results do not match, please start a new conversation and retry（上游 code=11148）`，
客户端连续自动重试 3 次全部失败（真实日志：`chat_request` ×3 → 最后一次 `chat_error`）。

### 2. 根因

ZCode 的 Responses `input` 在**并行工具调用**时为 `fc,fc → fco,fco → fc → fco`（两批调用各自带结果）。
转换器对 `function_call_output` 分支**没有立即冲刷待发结果**，且 `function_call` 分支**不先冲刷上一批结果**
即开启新 assistant，于是产出：

```
[11] assistant tool_calls=[C1,C2]   ← 批 1
[12] assistant tool_calls=[C3]      ← 批 2 插在批 1 结果之前 ✗
[13] tool → C1 [14] tool → C2 [15] tool → C3
```

上游要求「带 tool_calls 的 assistant 后**紧跟**它每条结果」，中间夹任何消息即判 11148。
注意 `_clamp_responses_call_id` 的 64 截断**不是**本 bug 原因（真实失败 id 均 32 字符）。

### 3. 修复记录（2026-10-09）

| 层次 | 实现 |
|---|---|
| 转换器修根 | `function_call` 分支先 `flush_tool_results()` 再开/续 assistant（批间守序）；`function_call_output` 分支对齐 9router `openai-responses.js` 先到先排——先推 assistant、再立即推送待发结果 |
| 出站安全网 | 新建 `relay/relay/tool_repair.py`（原 spec §4.5.3 规划落地，移植 `workbuddy2api-panel/internal/upstream/tool_pairing.go`）：`repack_tool_results` 把夹在 assistant.tool_calls 与其结果之间的非 tool 消息后移（含「下一组组头不被吞」守卫）；`cleanup_orphan_tool_calls` 按 id 集合双侧对称裁剪（**不做**「批内不全删整批」——那会留孤儿结果反倒制造 11148）。WorkBuddy adapter `transform_request` 接线：先 repack 再 cleanup（参考管线同序） |
| 打包 | `relay.spec` / `relay-onefile.spec` 双保险登记 `relay.tool_repair` |

### 4. 证据与回归

- A/B 实证（小号 2 请求，[复现-wb工具配对断裂.py](../spec/WorkBuddy聊天反代与多平台聚合/复现-wb工具配对断裂.py)）：修复前 A=400/11148、B=200；修复后 A 的转换器产出即修复形态且 **A/B 双双 200**；
- 单测 +17：`tests/test_tool_repair.py`（重排/双侧裁剪/零改动返原对象）+ `test_protocol_adapter.py`（交错双批、先到先排）+ `test_wb_chat.py`（adapter 集成）；全量 395 passed；
- 真实客户端多轮带工具复验（ZCode 经本地 relay）归用户在 GUI 完成。

## BUG-003 工具名伪装误伤 WorkBuddy/自定义供应商（**已修复 2026-10-09**）

> 状态：**已修复**（2026-10-09 第二轮；方案 A「只对牛码伪装」由用户拍板）
> 位置（修复前）：`relay/relay/routes.py::_handle_chat`（`build_disguise_context` 无条件执行）
> 影响等级：高。`Grep→Search`、`Skill→ReadSkill` 等改名直发上游——agent 回流的工具名对不上，工具链断裂。

### 1. 现象

WorkBuddy/自定义供应商链路发起带工具请求时，上游收到的工具名为牛码原生名
（`Search`/`ReadSkill` 等），agent 声明的原名（`Grep`/`Skill`）只在牛码链路的
`restore_map` 有还原路径——非牛码链路根本拿不到 ctx，改名后无任何还原。

### 2. 根因

`_handle_chat` 对**所有**供应商无条件执行 `tool_disguise.build_disguise_context`，
而 `build_adapter` 的非牛码分支（注册表/自定义）构造 adapter 时**不接收 ctx**。
三家参考（2api-panel / 9router / chatcoder）对 WorkBuddy 均**不做**工具名伪装
（WorkBuddy 上游原生支持任意工具名，B5 实证）——伪装本就是牛码专属需求（M3）。

### 3. 修复记录（2026-10-09）

| 层次 | 实现 |
|---|---|
| 门控 | `routes._handle_chat` 按 `model_ref.parse_model_ref_lenient(...).is_niucode` 分流：牛码 → 照旧伪装并下发 ctx；非牛码 → `ctx=None`，tools 原名透传 |
| 监控 | `tool_disguise` 事件仅牛码链路 emit；chat_done 的 map_hits/longtail/dropped 非牛码记 0（统计口径 = 牛码链路） |
| 内部 | `_sse_with_retry` / `_chat_with_retry` / `_refresh_provider_credentials` 签名放宽 `ctx: DisguiseContext \| None` |

### 4. 证据与回归

- 单测 +3：`test_model_prefix.py`（牛码仍伪装为 `Search` 且监控计数 +1；WorkBuddy `Grep` 原名直达 adapter 且不产生伪装监控）+ `test_custom_forward.py`（自定义供应商出站 body 工具原名断言）；
- 三家参考口径核验：2api-panel/9router/chatcoder 对 WorkBuddy 工具与 agent 系统提示词均不做伪装处理（本轮会话逐一读源码确认）。

## BUG-004 缺结果工具调用顶死会话（配对安全网「只裁不补」的缺口）（**已修复 2026-10-09**）

> 状态：**已修复**（2026-10-09 第二轮，与 BUG-003 同批）
> 位置（修复前）：`relay/relay/tool_repair.py`（仅 repack/cleanup 两层）
> 影响等级：中高。agent 历史里「有 tool_call 无结果」的调用被 cleanup 裁掉后工具上下文丢失；模型看不到「该结果丢失」提示。

### 1. 根因

原安全网只有 `repack`（归位）+ `cleanup`（裁孤儿）：缺结果的调用只能**裁掉**。
裁掉虽然让请求通过，但模型无从知晓「这轮工具调用发生过、结果丢了」，
可能基于残缺上下文继续推理。

### 2. 修复记录（2026-10-09）

- 新增 `fill_missing_tool_results`：给 assistant.tool_calls 中**缺结果**的调用补一条
  显式占位 tool 消息（`MISSING_RESULT_PLACEHOLDER`，明确「该结果缺失、勿依赖、
  必要时重跑」——对齐 chatcoder `ensure_tool_pairing` 的显式占位路线；
  9router `fixMissingToolResponses` 只补空串，占位文案对模型更友好）；
- 新增 `repair_tool_pairing` 一键三层：**fill → repack → cleanup**（参考管线同序；
  fill 先行保证占位可被 repack 一并归位）；

> 位置（修复前）：`frontend/src/Shell.vue`（业务页 `<component>` 无条件挂载）+ 各页 `onMounted` 即请求（`WorkBuddyTab`/`Overview`/`Logs`/`NiucodeModels`…）

### 2. 根因（时序竞态，与产物无关）

sidecar 是 PyInstaller onefile：冷启动需解包（~30MB）+ SQLite/数据目录初始化，**持续数秒**（本机实测首启 1–3s，冷缓更快/更慢因素多）。而前端业务页 `onMounted` 立即发请求，落在两个失败窗口：

2. **relay 就绪但鉴权 key 未装载窗口**：壳转发 `apiKey: _authKey`（前端 config store 装载后才回填），空 key → relay 401「缺少 Authorization」。

### 3. 修复记录（2026-10-12）

`frontend/src/Shell.vue` 加**首启就绪门控**（方案比「api.ts 请求层挂起等待」更简单可靠，不动请求漏斗）：

| 项 | 实现 |
|---|---|
| 门控条件 | `store.relay.running && configStore.loaded`（relay 就绪 **且** 鉴权 key 已装载）才放行业务页；此前显示居中占位「正在启动本地服务…」+ 呼吸灯 |
