# 真实请求反哺模型状态

> 状态：规划中
> 优先级：核心（模型页连通状态的真实性；依赖连通性测试-白名单豁免的 modelStatus 四态底座）
> 来源：2026-09-04 评估。模型页连通状态目前只由「显式测试」（登录/同步批量、手动测试）产生，**真实使用证据不回写**：① 模型标「失败」（旧测试快照）后开关启用、agent 实际使用正常，模型页仍显示失败；② 模型标「成功」（数小时前测试）后上游故障，agent 连发必挂，模型页仍显示成功。真实请求是比测试更可信的连通性证据，应反哺状态。
> 依赖：连通性测试-白名单豁免（modelStatus 四态：未测试/测试中/成功/失败 + probe 标记）；M6 数据底座与 relay monitor 事件（chat\_done / chat\_error 已带 model）；routes.py 聊天完成点（done/error 两处）
> 定稿日期：—（2026-09-04 已拍板：单独立项、判定口径=严格可达性判定；实现方案未定稿）

## 1. 背景与目标

### 背景

现状 `store.modelStatus`（success/failure/testing，会话级）只被三条显式路径写入：登录/同步后批量测试、手动「测试」、（已移除的）开关预检。agent 在 /v1/chat/completions 上的**真实对话结果不反哺**。relay 侧数据其实已存在：每次聊天结束均 monitor.emit + db 落 `chat_done` / `chat_error`，均带 model 字段——缺的是「把真实请求结果裁决为模型连通结论并暴露给 GUI」的闭环。

### 目标

| #  | 功能      | 说明                                                   |
| -- | ------- | ---------------------------------------------------- |
| F1 | 真实成功反哺  | 开关启用的模型：agent 真实请求成功（上游可达、正常结束）→ 模型状态变为「成功」          |
| F2 | 真实失败反哺  | 模型「成功」是旧快照、上游随后故障 → agent 请求出现**可达性失败** → 状态变为「失败」   |
| F3 | 严格可达性判定 | 判定「成功/失败」仅以**上游可达性**为准：内容/参数级失败（超长上下文、策略拦截等 400）不判失败 |
| F4 | 统一证据源裁决 | 测试 probe 与真实使用结果写入同一裁决（最新证据覆盖旧证据），可标注来源 test/use     |
| F5 | GUI 闭环  | 模型页 / 概览页轮询拉到裁决后刷新四态标签；无需重启、无新鉴权通道（沿用 api-key）       |

### 非目标

- ❌ 不做**主动健康巡检**（定时给启用模型发 probe）——本需求只被动消费「真实请求 + 手动/自动测试」产生的证据。

- ❌ 不做失败原因分级 UI（上游 500 / 超时 / 内容 400 的 tooltip 细分）——裁决数据可留字段，展示另议。

- ❌ 不改 agent 侧行为 / 不改 OpenAI 协议语义。

- ❌ 不改 vendored `relay/app/**`。

## 2. 设计方案（候选；倾向路线 A，未定稿）

### 关键实现缺口（两条路线共有，先摆出来）

判定「真实请求=可达性成功/失败」需要的信息当前**不完整**：

- relay 侧区分失败类别：provider 对上游非 200 一律抛 `RuntimeError("模型请求失败 {status}：{text}")`（[ta3.py](../../../relay/app/models/providers/ta3.py)），**4xx 内容级与 5xx/网络/超时未结构化区分**；超时/断流在部分网关路径走 finish\_reason=timeout 但仍落 `chat_done`（finish\_reason 未入事件）。

- 因此需在 chat 完成点结构化记录：`finish_reason`（done 侧）与 `error_kind ∈ {upstream_http, timeout, network, content_rejected, …}`（error 侧）。流式分支目前只透出 usage，不透 finish\_reason——需要 `oai_adapter`（自研，可改）在流式结束时回传 finish\_reason。

- 内容级 400 的判定：按 status 分段 + 上游 body 关键词（context/length/token/abuse/content policy…）粗判，**如实承认不可穷尽**；拿不准的 4xx 保守处理策略定稿时拍板（倾向：4xx 全不判「可达性失败」、仅 5xx/网络/超时判失败，最稳但会漏真实故障）。

### 路线 A：relay 进程内模型健康裁决（推荐）

- 新增进程内缓存 `model_health: dict[model] = {verdict: success|failure, ts, source: test|use}`（内存态，随进程重启清空，与 modelStatus 会话级语义一致）。

- 写入点：routes.py 两条聊天结束路径（chat\_done / chat\_error），**probe 与普通请求都写**，probe 来源标记 `test`、普通请求 `use`。

- 严格口径的裁决函数（纯函数，便于单测）：输入 finish\_reason / error\_kind → verdict；内容级 400 → 不写（或写但标记 unknown，定稿选一）。

- 暴露 `GET /v1/models/health`（Depends(require\_api\_key)），返回 `{model: {verdict, ts, source}}`。

- GUI：模型页 / 概览页在激活时轮询 health（\~3-5s），把 verdict 并入 modelStatus 显示；手动测试的即时反馈仍走本地赋值，与 health 轮询结果一致收敛（测试也写 health）。

- 优点：错误类别/finish\_reason 在 relay 侧最全，严格口径可落地；GUI 纯消费。

- 代价：relay 增状态 + 端点 + 单测；需补流式层 finish\_reason 透出与错误分类（自研可改）。

### 路线 B：纯前端轮询 monitor/events 聚合（否决留档）

- Models 页拉 `/v1/monitor/events` 自行翻译 chat\_done/chat\_error。

- 否决理由：事件里没有 finish\_reason/错误类别，无法做「严格可达性判定」（只能 chat\_error 全判失败 → 内容级误标）；裁决规则散在前端，多页不一致风险高。

## 3. 已知边界 / 风险

- **内容级失败的边界不可穷尽**：严格口径依赖 status + 关键词粗判，无法 100% 区分；倾向「4xx 不判可达性失败」的保守策略会在上游真故障时漏判（回退靠手动测试）。定稿时需在「漏判」与「误标」间取舍并记录。

- **抖动敏感**：以「最近一次真实请求」为结论时，单次网络抖动会闪红/闪绿。后续可升级「最近 N 次多数」，本需求不做。

- **多页一致性**：健康裁决在 relay 内存，任何来源（含 agent 直连、其他 GUI 进程/会话）的请求都反映；GUI 轮询窗口内可能滞后数秒。

- **进程重启即清空**：回「未测试」，直到下一次测试或真实请求（与现有会话级语义一致）。

- **401 刷新后重试成功不算失败**：重试成功才落 done；仅重试后仍失败才落 error。

- 若改 relay，需重建 sidecar + NSIS 才进 GUI（开发态直跑不受影响）。

## 4. 验收（待方案定稿后补充实现细节）

1. 模型状态「失败」且开关启用 → agent 真实成功请求后，`/v1/models/health` 该模型变 success，模型页轮询后标「成功」。
2. 模型「成功」（旧快照）且开关启用 → agent 连续上游 5xx/超时后，health 变 failure，页面标「失败」。
3. 内容级失败（如超长上下文 400）不把模型判为失败（F3）。
4. probe 测试与真实请求统一裁决：最新证据覆盖旧证据，来源可区分 test/use（F4）。
5. relay 单测覆盖裁决函数（done/error 序列、error\_kind 映射、内容级豁免）+ health 端点鉴权；前端 build；小号冒烟一条。
