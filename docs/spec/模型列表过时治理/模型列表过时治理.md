## 1. 背景与目标

### 现象

牛码目录（`/v1/auth/sync` 拉取）与 WorkBuddy 目录（`/v3/config` ∪ 企业端点）在供应商页模型区与
`/v1/models` **全量展示**。**2026-10-10 实测**（dev 环境 `/v1/models?all=1`，共 51 条）：

| 分组 | 数量 | 说明 |
|---|---|---|
| 牛码 | 5 | 全部有思考档位（glm-5.3 / kimi-k3 / deepseek-v4 系） |
| WorkBuddy · 有档位 | 15 | hy3/hy4 系、glm-5.3/5.2、kimi-k3-1/k2.8、deepseek-v4 系、space-bunny 等新代 |
| WorkBuddy · 无档位 | 31 | 14 条不支持思考（glm-4.6、wb-lite、deepseek-v3 旧代…）+ 17 条支持但无档位（`auto`/`fast-model`/`balanced-model`/`deep-model` 别名、kimi-k2 系…） |

用户观察：「不支持思考 / 没有思考档位」的模型 ≈ 过时模型（目录仍在下发、但已不是新代）；
希望这批模型**默认隐藏**，而不是逐条手动关（现状 31 条无档位模型均处于启用/可见状态）。

### 拍板结论（2026-10-10，用户）

1. **默认隐藏**无思考档位（`reasoning_efforts` 为空）的 WorkBuddy 模型；
2. WorkBuddy tab「添加账号」按钮旁新增**「模型显示」**设置按钮：弹窗列出**全部**拉取到的
   WorkBuddy 模型，逐条开关控制「显示 / 隐藏」；
3. 不照抄三家任一方案（§3）——以 9router 的「手动名单 + 列表过滤 + 弹窗管理」为交互基底，
   叠加「无档位默认隐藏」的自动默认值（三家均无此默认）。
4. **两个开关联动**（同日二次拍板）：隐藏 ⇒ 显示/启用**双开关同关**（列表消失 **且** 不可调用，
   chat 404）；从隐藏恢复显示 ⇒ **双开**（恢复可调用）。主列表「启用」开关仍可单独操作
   （保留「可见但停用」状态）。

### 目标

- F1 过时模型**不必逐条手动**屏蔽：无档位模型开箱即隐 **且即停用**，用户只需处理例外；
- F2 误杀**可恢复**：默认判定是启发式，错杀（隐藏+停用）经「模型显示」一键恢复；404 文案引导到
  供应商页（判定宁保守勿激进：仅「无档位」触发，有档位模型不动）；
- F3 GUI 主列表、`/v1/models`（agent 侧）与 chat 门控同源一致：均按「可见性 ∩ 白名单」判定，
  口径由 relay 单点计算；
- F4 两个开关语义与联动明确：显示=列表呈现 + 启停主导；启用=可用性（可单独关）；**隐藏 ⇒ 两者
  皆关**，见 §4.1。

### 非目标

- ❌ 不做「上游不存在的模型」的凭空编造——目录始终以上游下发为准（2api-panel 纯动态原则）；
- ❌ 不改编排/转发主链路：仅在既有 `_ensure_*` 门控（与白名单同点位）加入可见性条件，
  隐藏 → 404（联动停用，见 §4.1）；
- ❌ 不做「自动识别官方下线」（真实请求反哺留作后续增强，见 §4.6 被否决备选）；
- ❌ 本期不做牛码/自定义供应商侧治理（牛码 5 条全有档位，无实际需求；机制按前缀可扩展）。

## 2. 现状机制盘点

| 机制 | 现状 | 与本需求的关系 |
|---|---|---|
| 白名单（启用/禁用） | 供应商页开关逐条启停；空=全启用；`[DISABLE_ALL]` 哨兵；`/v1/models` 过滤（`routes.py::list_models` 517-523）+ chat 404 拦截（`_ensure_model` 346/353）；写 `relay_state.json` 的 `config.model_whitelist` | **联动维度**（2026-10-10 修订，原「正交」口径作废）：显示开关主导启停（隐藏 ⇒ 双关）；chat 门控加可见性条件；白名单仍可单独关（保留「可见但停用」） |
| 目录来源 | 全动态：牛码 sync、WorkBuddy 双端点并集（v3 为主）；无静态兜底名单 | 过时模型来自**上游仍在下发**的条目——不能靠「不编造」解决 |

| 非对话模型过滤 | WorkBuddy 目录过滤 `maxOutputTokens ≤ 256` / `tags` 含 `text-to-image` / 前缀黑名单（`catalog.py::_non_chat_model`） | 已有「结构性过滤」先例；本需求是「时效性/能力性过滤」，落在呈现层 |
| 可见性（显示/隐藏） | **无此概念**（全仓无模型 visible/hidden 字段） | 本期新增 |
| 真实请求反哺模型状态 | 规划中（独立需求） | 本期**不依赖**；未来可作自动默认的增强证据源 |

## 3. 三家参考口径与拍板结论（2026-10-09 调研，2026-10-10 拍板）

| 项目 | 做法 | 要点 / 借鉴价值 |
|---|---|---|
| **9router** | 手动禁用名单：GUI 按供应商勾选 → `disabledModels` KV（per-provider）→ `/v1/models` 过滤（`isDisabled` 跳过）；REST `/api/models/disabled` GET/POST/DELETE。**禁用不进聊天链路**（仓库内 `isDisabled` 仅出现于 models 路由与 zedAuth，聊天链路未见引用） | **交互基底**：名单 + 列表过滤 + 弹窗逐条管理；差在没有「默认值」 |
| **2api-panel** | 纯动态：`/v1/models` 只透出上游实际下发（CN `/v3/config` + global 探测并集）；无兜底名单 | 口径权威（列表=上游真实下发）；但不提供治理机制，治不了「上游仍在下发的过时条目」 |
| **chatcoder** | 静态元数据目录（保守取值）辅助 lookup（补 context_window 等） | 关联弱：不做过时过滤、只补元数据 |

**拍板结论**：不照抄任一家——三家都没有用户要的「**默认隐藏 + 联动停用**」。取 9router 的
交互形态（手动名单 + 列表过滤 + 弹窗逐条开关）；默认值规则由用户拍板：「WorkBuddy 前缀 +
无思考档位 → 默认隐藏」；联动规则由用户二次拍板：「隐藏 ⇒ 双关（不可调用）；恢复显示 ⇒ 双开」。
**有意与 9router 不同**：其禁用名单仅过滤列表、不进聊天链路（隐藏模型仍可按名调用）；本方案
「隐藏即停用」（chat 404）——过时模型应彻底下线，而非列表里藏起来仍被 agent 按旧名调用。
牛码与自定义供应商不参与默认规则（恒可见可调）。

## 4. 设计方案（定稿）

### 4.1 概念模型：显示主导的双开关联动（2026-10-10 二次修订）

两个开关：**显示/隐藏**（新）与**启用/禁用**（白名单，既有）。联动规则：

| 操作 | 显示开关 | 启用开关 | 效果 |
|---|---|---|---|
| 主列表直接开/关「启用」 | 不变 | 单独变 | 「可见但停用」状态保留（404 语义与现状一致） |
| 弹窗**隐藏**某模型 | → 关 | **→ 关（成对写入）** | 列表消失（GUI + agent 侧）**且** chat 404＝「过时模型彻底下线」 |
| 弹窗**显示**某模型（从隐藏恢复） | → 开 | **→ 开（成对写入）** | 恢复可见 + 可调用（误杀一键恢复） |
| 弹窗「全部显示」（批量） | 隐藏项批量写 show | 并入白名单（三态合并，见 §4.5） | 批量恢复可见可用 |
| 弹窗「恢复默认」（批量） | 清空 override | **不动白名单**（仅清显示覆盖；将变隐藏者由门控天然 404） | 回 §4.2 默认判定 |

- **隐藏态下「启用」开关的呈现**：呈关且置灰不可交互——「隐藏但启用」无实际效果（门控必 404），
  需先开「显示」（双开）再按需单独关「启用」。
- **语义定位**：显示开关是「推荐位 + 总闸」——隐藏即双关（过时模型不再被 agent 按旧名调用，
  这是本需求的目的）；启用开关是「可用性微调」——保留可见但停用的单独状态（巡检、临时停服）。
- **成对写入**落在前端一次 `config.update()` 里（`model_visibility` + `model_whitelist` 同时提交；
  后端 `auth_config_update` 已支持两字段同批校验/落盘，无需新协议）。
- **chat 门控**：`_ensure_model` / `_ensure_provider_model` 在既有白名单判定后追加可见性判定
  （隐藏 → 404「未知或未启用的模型」；点位与白名单相同，口径 = 「可见 ∩ 启用」）。
- **默认隐藏的联动效果**：无档位 WB 模型默认即「隐藏+停用」——agent 侧列表不出现、按旧名调用
  404；在弹窗中一键显示即恢复（无需记得去开第二个开关）。
- 与 9router 的**有意差异**：其禁用名单仅过滤列表、不进聊天链路；本方案隐藏即停用
  （用户二次拍板：过时模型应彻底下线，而非列表里藏起来仍能被按旧名调用）。

### 4.2 判定规则（effective visibility，relay 单点计算）

```
visible(条目) = model_visibility[全名]     若存在用户覆盖（"show" / "hide"）
              = False                      若 WorkBuddy 前缀 且 reasoning_efforts 为空
              = True                       其它（有档位 WB / 牛码 / 自定义供应商）
```

- **默认（无需任何落盘）**：「WorkBuddy 前缀 + 无档位」→ 隐藏（联动停用，见 §4.1）。谓词
  `not reasoning_efforts` 同时覆盖用户点名的两类（不支持思考 14 条；支持但无档位 17 条）。
- **用户覆盖**：弹窗里动过的模型写 `model_visibility`（全名 → `"show"`/`"hide"`），
  **覆盖优先于默认**——手动打开的模型不会被目录抖动藏回去；手动隐藏的有档位模型保持隐藏。
- **持续默认**：目录刷新（1h）后，新出现的无档位模型自动默认隐藏、有档位自动显示；
  已覆盖的不受影响。
- 别名（`auto`/`fast-model`/`balanced-model`/`deep-model`）按同一规则默认隐藏，用户可在弹窗开启
  （不做特判，见 §4.6）。

### 4.3 存储（`relay_state.json` config 段）

新增 k/v：`config.model_visibility`，形如 `{"WorkBuddy/auto": "show", "WorkBuddy/wb-lite": "hide"}`；
**只存用户显式覆盖**，缺省为空 dict（未覆盖=按 §4.2 默认规则）。

- `relay/relay/storage.py` 新增 `get_model_visibility()` / `save_model_visibility()`（对齐
  `model_whitelist` 283-304 的读/写/归一模式）：读损坏回退 `{}`；键经 `model_ref.canonical_key`
  归一为全名；值仅接受 `"show"` / `"hide"`。
- `/v1/auth/config`：GET 增加 `model_visibility` 字段；POST（部分更新）增加校验——`dict[str, str]`、
  值 ∈ {show, hide}，否则 400 不落盘（沿用 `auth_config_update`「全字段先校验」模式，routes.py 949-978）。
- **成对写入**：`model_visibility` 与 `model_whitelist` 由前端一次提交（同批校验、同批落盘），
  见 §4.1；后端无需新增联动逻辑（联动是前端语义，持久化层两键独立、可分别回放）。

### 4.4 relay 接口

- **`GET /v1/models?all=1`（GUI 用）**：每条目增加 `visible: bool`（`_all_model_entries` 内统一
  读一次 override 计算）。完整目录语义不变（**不**做可见性/白名单过滤）——弹窗需要看到全部（含隐藏）。
- **`GET /v1/models`（agent 侧，all=0）**：过滤 = 可见性 ∩ 白名单（不变式：隐藏 ⇒ 已停用）：
  `data = [m for m in entries if m.visible and (not wl or m.id in wl)]`（`[DISABLE_ALL]` 分支保持）。
- **`GET /v1/models/{id}`（单模型）**：不过滤可见性（与现状不过滤白名单一致）。
- **`/v1/auth/config`**：读写 `model_visibility`（§4.3）；与 `model_whitelist` 可同批提交。
- **chat 门控（`_ensure_model` / `_ensure_provider_model`）**：白名单判定后追加可见性判定——
  隐藏的 WB 模型 → 404「未知或未启用」（与白名单同为 404 点位，不动转发主链路）。

### 4.5 GUI（WorkBuddy tab）

- **入口**：`WorkBuddyTab.vue` 账号区 head 行（326-337）「添加账号」按钮旁新增「模型显示」
  （`NButton size="small"`）。
- **弹窗**（`NModal preset="card"`，~640px，对齐现有弹窗惯例）：
  - 列表 = **全部** WorkBuddy 模型（含隐藏；弹窗内滚动 + 搜索框，复用主列表搜索模式）；
  - 每行 = 模型名（全名，可复制）+ 思考档位信息（有档位列出 level；无档位灰字「无档位」——
    解释默认隐藏来源）+ **一个 `NSwitch`（显示）**（2026-10-11 用户验收反馈简化：原「显示+启用
    双开关」的启用列冗余（联动下隐藏态必双关），去掉后单开关点击即同批双写显示+启用，
    见 §4.7 三版）；
  - **开关联动（前端语义）**：
    - 关「显示」→ 同一次提交里把该模型从白名单移除（成对写入 `model_visibility.hide` +
      `model_whitelist` 去该项）；
    - 开「显示」（从隐藏恢复）→ 同一次提交里把该模型加进白名单（双开）；
    - 已在显示态时单独关「启用」→ 只写 `model_whitelist`（不动显示，保留「可见但停用」）；
  - header 操作：「全部显示」（对当前隐藏的全部**双开**）、「恢复默认」（确认后清空 override，
    回 §4.2 默认）；footer 仅「关闭」；
  - 开关**即时保存**：`config.update({ model_visibility: {...}, model_whitelist: [...] })`（沿用配置
    真值「响应回执整体回写」模式），成功后**重拉 `all=1`** 刷新 `visible`——前端不复刻判定规则
    （口径由 relay 单点计算）；白名单成对写入的合并规则复用现有 `onToggleModel` 的三种名单态
    （空=全启用 / `__none__` 哨兵 / 显式名单）处理。
- **主列表**：仅展示可见的 WB 模型（`wbModels = 全量WB.filter(m => m.visible !== false)`，缺字段
  防御性视为可见）；被隐藏模型只出现在弹窗。主列表「启用」开关语义/位置不变（单独可用）。
- **其它消费点**：`Overview.vue` 首页模型卡等 `all=1` 消费处同步按 `visible` 过滤（实现时一并处理）。
- 前端类型：`api.ts` `Config` 增 `model_visibility: Record<string, 'show' | 'hide'>`、`OaiModel`
  增 `visible?: boolean`；`stores/config.ts` state 初始值 `model_visibility: {}`。

### 4.6 被否决的备选与否决理由

> 修订说明（2026-10-10 二次拍板后）：原「隐藏不拦截调用（列表治理）」口径被用户否决，
> 改为「隐藏即停用」；下表相应行已按新口径标注。

| 备选 | 否决理由 |
|---|---|
| 照抄 9router（纯手动名单，无默认） | 用户拍板否决：不解决「默认」，31 条仍需逐条手动关，痛点原样保留 |
| 照抄 9router 的「仅列表过滤、不进聊天链路」 | 用户二次拍板否决：过时模型应**彻底下线**——只从列表藏起来、agent 按旧名仍可调用，治理不彻底（本方案改为隐藏即停用） |
| 照抄 2api-panel（纯动态无兜底） | 治不了「上游仍在下发的过时条目」——正是本需求要解决的场景 |
| 照抄 chatcoder（静态元数据） | 它不做过时过滤、只补元数据，关联弱 |
| **白名单承载**（默认禁用 / 一键写白名单，不加显示维度） | ① 白名单空=全启用语义使「默认」需每次目录刷新重算全量名单，复杂且有竞态；② 与用户「显示/隐藏」语义不符（用户要的是可见性开关主导）；**联动后白名单仍保留**（弹窗/主列表的启用开关），但仅作「可见但停用」的微调维度 |
| 仅前端过滤（不动 `/v1/models` 与 chat 门控） | ① agent 客户端仍全量可见（用户列表观感来源之一）；② 前后端双份口径易漂移（违反 F3）；③ 联动停用需 chat 门控，纯前端物理上做不到 |
| **纯可见性、不做联动**（初版方案：隐藏仅影响列表） | 初版曾按「防误杀」原则定为仅列表过滤；用户二次拍板改为联动（隐藏即停用）——误杀恢复手段以「弹窗一键显示（双开）」替代，判定仅「无档位」触发、面窄且可恢复 |
| 静态快照名单（应用一次默认后写死） | 目录动态增删（1h 刷新）时不跟随：新无档位模型不会自动隐藏；纯静态与纯动态两端都不取，取「动态默认 + 用户覆盖」 |
| 别名特判保留显示（auto/fast-model/…） | 需硬编码别名清单、新别名易漏、规则不统一；改为同规则 + 弹窗手动打开 |
| 原方案 B：真实请求反哺证据驱动自动标记/禁用 | 依赖未落地需求（长期可达性观测）；自动禁用误杀风险大；留作**后续增强候选**（可作默认规则的补充证据源） |
| 原方案 C：上游 tags/credits 自动判「官方下线」 | 实测条目未携带该语义（`_to_entry` 丢弃 `credits`/`tags` 仅作过滤）；不可靠 |

## 5. 已知边界

- 「过时」无官方标准，默认判定为**启发式**（无档位≈旧代）；上游字段抖动可能让个别模型的默认
  呈现变化。**联动后默认隐藏=默认停用**：误杀会表现为 agent 调用 404——恢复手段是弹窗「显示」
  （一键双开）；弹窗始终列出全部，模型不丢。
- **隐藏即停用**（chat 404，与白名单同为否定语义）；「可见但停用」状态仍保留（主列表单独关启用）。
- 目录 1h 缓存：新增/下线模型到下次刷新才反映；`model_visibility` 的生效不依赖目录刷新。
- 牛码与自定义供应商本期不参与判定（`visible` 恒 true）；机制按前缀可扩展。
- 「全部显示」对**当下目录**内隐藏项执行双开；此后新出现的无档位模型仍按默认隐藏（语义如此）。
- 目录中消失的模型若留有 override 键，无害保留（重新上线时恢复用户意图；白名单项同理不清理）。
- agent 端已缓存旧目录的场景：启用中的可见模型不受影响；被隐藏（停用）模型按名调用 404——
  这正是「过时模型彻底下线」的预期表现（404 文案引导到供应商页）。
