# 模型列表过时治理

> 状态：规划中
> 优先级：交付（模型页/供应商页列表观感与可用性；不影响聊天主链路）
> 来源：2026-10-09 用户提出——模型列表（牛码目录 + WorkBuddy 目录）展示出来有很多已过时的模型，需要治理；三家参考各有做法，**单独立项选型（用户拍板参考其一）**。
> 依赖：无硬依赖。可选的证据协同：真实请求反哺模型状态（可作为「自动识别过时」的证据源，见 §3 方案 B）。
> 定稿日期：—（方案未定稿；本文先固定问题域、现状盘点与三家参考口径）

## 1. 背景与目标

### 现象

牛码目录（`/v1/auth/sync` 拉取）与 WorkBuddy 目录（`/v3/config` ∪ 企业端点，54 个含
`auto`/`fast-model`/`balanced-model`/`deep-model` 别名与旧版本型号）在供应商页模型区与
`/v1/models` **全量展示**，其中不少是上游已不推荐/不可用的「过时」模型；用户目前只能
逐条手动关开关（白名单）屏蔽，操作成本高且好模型/过时模型混排。

### 目标（具体口径待定稿细化，先列方向）

- F1：过时模型**不必逐条手动**屏蔽（批量 / 标签化 / 自动识别三者取一或组合）；
- F2：**不误伤可用模型**（判定宁保守勿激进——过时判定错杀会静默丢模型）；
- F3：GUI 与 `/v1/models` 两侧口径一致（agent 侧列表与 GUI 列表同源）；
- F4：与既有白名单机制的关系明确（并存 / 分层 / 合并，见 §3）。

### 非目标（先行排除）

- ❌ 不做「上游不存在的模型」的凭空编造——目录始终以上游下发为准（2api-panel 纯动态原则）；
- ❌ 不改聊天路由/转发主链路（本需求只动「列表呈现与筛选」）。

## 2. 现状机制盘点（避免重复造轮子）

| 机制 | 现状 | 与本需求的关系 |
|---|---|---|
| 白名单（启用/禁用） | 已实现：供应商页开关逐条启停；空=全启用；`[DISABLE_ALL]` 哨兵；写 `relay_state.json` | **已是「手动黑名单」大半底座**（方向：本需求是「屏蔽过时」，白名单是「禁用任意」） |
| 目录来源 | 全动态：牛码 sync、WorkBuddy 双端点并集（v3 为主）；无静态兜底名单 | 过时模型来自**上游仍在下发**的条目——不能靠「不编造」解决 |
| 非对话模型过滤 | 已实现：WorkBuddy 目录过滤 `maxOutputTokens ≤ 256` / `tags` 含 `text-to-image` / 前缀黑名单 | 已有「结构性过滤」先例；本需求是「时效性过滤」 |
| 真实请求反哺模型状态 | 规划中（`真实请求反哺模型状态` 需求） | 可作方案 B 证据源：长期 11102/404 的模型自动标记 |

## 3. 三家参考口径（2026-10-09 调研，选型依据）

| 项目 | 做法 | 要点 / 借鉴价值 |
|---|---|---|
| **9router** | **手动禁用名单**：GUI 按供应商勾选「禁用模型」→ 落库（`disabledModels` KV，per-provider `[id…]`）→ `/v1/models` 过滤（`isDisabled(alias, model.id)` 跳过）；REST `/api/models/disabled`（GET/POST/DELETE） | **与我们的白名单同构**（方向相反：它是黑名单，我们是白名单）；「批量禁用 + 一键解禁」的 GUI 交互值得抄；无自动识别 |
| **2api-panel** | **纯动态**：`/v1/models` 只透出上游实际下发（CN `/v3/config` + global 探测并集）；无静态名单兜底（注释直言「假名单只会让客户端选到 11102 的模型」，产品决策：无兜底） | 不给「过时治理」直接机制，但**口径权威**：列表=上游真实下发；其 global 逃生门（`GlobalEnabled` 开关默认关）是「少而精」的另一种解法 |
| **chatcoder** | 静态元数据目录（保守取值）辅助 lookup（精确/归一化/前缀匹配补全 context_window 等） | 关联弱：它不做过时过滤，只补元数据；可借鉴「静态表只做补充、不做白名单」的边界 |

**选型倾向（待用户拍板）**：**9router 路线**——手动禁用与现有白名单几乎同构，扩展成本
最低（GUI 补「批量禁用过时/按标签筛」交互即可）；自动识别（方案 B）留作后续增强。

## 4. 候选方案（未定稿）

- **方案 A（9router 式，倾向）**：白名单扩展——供应商页补「批量禁用 / 一键解禁 / 按预览标记选」；
  `/v1/models` 已按白名单过滤（现成），工作量集中在 GUI。
- **方案 B（证据驱动，可选增强）**：叠加「真实请求反哺模型状态」——模型连续 N 次
  可达性失败（11102/404 类）→ 模型页标「疑似过时」徽标（不自动禁用，防误杀）；
  用户可一键禁用/解禁。依赖另一需求的裁决数据。
- **方案 C（上游标签驱动）**：若上游目录字段（`tags`/`credits`/目录变更历史）能直接判
  「官方已下线」，按标签自动折叠（需实测上游字段是否有此语义，尚未验证）。

三方案可组合：A 先行保底，B 作自动化增强，C 作锦上添花。

## 5. 已知边界

- 「过时」无官方标准：上游可能只是暂时下线又恢复（自动禁用有风险，倾向只标记不自动关）；
- 牛码与 WorkBuddy 目录语义不同（前者 sync 快照、后者随套餐账号差异），判定/过滤需分平台设计；
- 目录刷新（1h 缓存）后列表会变，「过时标记」的重算时机需定义。
