## 1. 背景与排查结论

### 1.1 症状

- CC Switch 里 CoderProxy 显示「需要路由」，但 `/v1/models` 能正常返回 3 个模型（`kimi-k3` / `deepseek-v4-flash` / `deepseek-v4-flash-vision-exp`），API Key 鉴权正常。
- **Codex CLI 直连时「一直重连、最终失败，CoderProxy 里连日志都没有」**——请求根本没到达 CoderProxy。

### 1.2 根因（已核实代码）

| 层 | 当前 CoderProxy 支持 | 说明 |
| -- | ---- | ---- |
| 入站（agent → relay） | **仅 `/v1/chat/completions`**（`oai_adapter.py` 只解析 `messages[]`） | 无 `/v1/responses`、`/v1/messages` 入口 |
| 内部 | 统一为 `ChatRequest` | 参考实现 vendored 的数据结构 |
| 出站（relay → 牛码） | **两种，按模型 `anthropic` 标记自动切** | `{apiBase}/chat/completions` 或 `{apiBase}/v1/messages` |

Codex CLI 默认走 OpenAI `/v1/responses`（请求体用 `input` 字段而非 `messages`），CoderProxy 入站不认 → 请求被拒/失效 → 连日志都未产生。

### 1.3 牛码实际支持哪种出站协议

代码证据（`relay/app/models/providers/ta3.py` `_stream_llm`）：

```python
if self._anthropic:
    url = f"{self._base_url}/v1/messages"      # Anthropic 格式
else:
    url = f"{self._base_url}/chat/completions"  # OpenAI 格式
```

`base_url` 取模型目录 `apiBase`；`anthropic` 标记由 vendored `catalog.py::_is_anthropic` 判定（provider=kimi/anthropic，或名字含 claude/kimi，或 apiBase 含 `/anthropic`）。

**结论：牛码出站吃两种协议（OpenAI `chat/completions` + Anthropic `v1/messages`），但没有 `/v1/responses`。**

## 2. 三种协议格式一致性确认

业界主流（面向 agent 的 LLM API）为以下三种，均已核实：

| 端点 | 协议 | 鉴权头 | 入站关键字段 | 出站关键字段 |
| -- | ---- | ---- | ---- | ---- |
| `/v1/chat/completions` | OpenAI Chat Completions | `Authorization: Bearer` | `messages[]` | `choices[].message` |
| `/v1/responses` | OpenAI Responses API（新一代） | `Authorization: Bearer` | `input[]` | `output[]` |
| `/v1/messages` | Anthropic Messages API | `x-api-key`（**非 Bearer**） | 独立顶层 `system` + `messages` | `assistant message` |

参考：sub2api（`D:\Code\github-project\sub2api`）已完整实现三协议互转，其 `backend/internal/pkg/apicompat` 包提供了 Anthropic ↔ Responses ↔ ChatCompletions 的双向转换，验证了「三种格式确实能互转」这一前提。

## 3. 三套候选方案

三套方案**最终出站都复用现有牛码协议切换（chat/messages）**，差异仅在「入站协议如何被识别并转成内部 `ChatRequest`」。

### 方案 A：入站多一道转换（自动识别入站协议）

- 新增 `/v1/responses`（及可选 `/v1/messages`）入口，按请求体特征自动判定协议：
  - `body 有 input 字段` → Responses
  - `body 有 messages 数组 + Bearer` → Chat Completions
  - `body 有独立顶层 system 字段 + x-api-key` → Anthropic
- 全部归一成现有 `ChatRequest`，出站零改动。
- 优点：结构最简、少配东西、无需多 Key。
- 缺点：识别靠 body 特征（一般可靠，但 Anthropic 的顶层 `system` 与 Chat 的 `messages[].system` 需靠「顶层是否有独立 system 字段」区分）。

### 方案 B：sub2api 平台分流（最全）

- CoderProxy 建分组/平台概念，协议身份由 Key 所属分组的 `Platform` 字段决定（对标 sub2api `getGroupPlatform`）。
- 完整实现三协议双向转换库（请求/响应/流式三级）。
- 优点：识别最强、可扩展三协议、天然满足「不同 Key 绑格式」。
- 缺点：转换代码量最大，属「大而全」，对当前「只要 Codex CLI 能用」的目标属过度设计。

### 方案 C：不同 Key 对应不同格式

- 建多个 API Key，每个 Key 显式绑定一种协议；agent 填 Key + 对应格式即可。
- 本质是「方案 A 的识别方式」改为「显式配置」：转换逻辑同一套，仅「如何知道是哪种协议」不同。
- 优点：无歧义、CC Switch 手动可控。
- 缺点：多一层 Key↔协议映射管理。

### 三套方案对比

| 维度 | A 入站自动识别 | B sub2api 平台分流 | C Key 绑格式 |
| ---- | ---- | ---- | ---- |
| 入站识别方式 | body 特征自动判断 | Key 分组 Platform | Key 显式绑定 |
| 是否需配多 Key | 否 | 是 | 是 |
| 出站（牛码） | 复用现有 | 复用现有 | 复用现有 |
| 转换代码量 | 最小 | 最大 | 中 |
| 识别鲁棒性 | 靠 body，可能误判 | 最强 | 最强 |
| 解决 Codex CLI | ✅ | ✅ | ✅ |

> 推荐：当前目标（Codex CLI 可用）优先 **方案 A**；若后续要「CC Switch 手动控制每种供应商格式」可在 A 基础上叠加 C 的显式绑定；方案 B 留作长期演进。
>
> **A→B 可平滑升级**：A 与 B 差异只在「识别层」（A 靠 body 特征自动判断，B 靠 Key 分组 Platform），下面的「转换层（协议→ChatRequest）」与「出站层（复用 Ta3Provider）」A/B **共用同一套代码**。二者结构同构：

```text
方案 A：                                 方案 B：
agent 请求                                  agent 请求
  ↓ 识别层：看 body 特征自动判断协议             ↓ 识别层：看 Key 分组 Platform
  ↓ 转换层：协议 → ChatRequest  ←【A/B 共用】    ↓ 转换层：协议 → ChatRequest
  ↓ 出站层：→ 按模型切 chat/messages ←【A/B 共用】  ↓ 出站层：→ 按模型切 chat/messages
```

实现 A 时只要把「转换层」与「识别层」分离开、留好识别接口，以后切 B 只需在识别层加「读 Key 配置的 Platform」分支，转换层与出站层一行不改（转置层本身若只做了 Responses→ChatRequest，则升 B 需补全 Anthropic→ChatRequest 等，属「扩展成本」而非「架构迁移成本」）。

## 4. 方案 A 实施步骤（三端点全加入站转换器字段映射）

> 目标：**三种入站端点全支持**——`/v1/chat/completions`（已有）、`/v1/responses`、`/v1/messages`（新增），统一归一成现有 `ChatRequest`，**出站复用现有 Ta3Provider（零改动）**。工程约定：入站转换器与识别层分离，为未来升 B 留接口。
>
> **实施顺序建议**：入站转换器先行（三种入站立刻能发请求、收文本回复）；响应方向组装按「chat 最简单 → messages 中等 → responses 最难」分步补，工具调用/流式复杂场景最后完善。

### 4.1 分层设计

```
入站识别(route) ──选协议──> 入站转换器(parse) ──产出──> ChatRequest ──复用──> Ta3Provider
   detect_protocol()            responses_to_chatrequest()                     出站零改动
```

- **识别层**：`detect_protocol(body)` 看顶层字段自动判断协议（`input` → Responses；`messages` + Bearer → Chat；独立顶层 `system` + `x-api-key` → Anthropic）。
- **转换层**：新增 `responses_to_chat_request(body)`（对标现有 `oai_adapter.oai_request_to_chat_request`）。此层 A/B 共用，为未来升 B 复用。
- **出站层**：复用现有 `build_provider` + `Ta3Provider`，零改动。

### 4.2 入站转换器：Responses → ChatRequest 字段映射

对照现有 `oai_request_to_chat_request`（`relay/relay/oai_adapter.py`），新增 `responses_to_chat_request`，核心是**把 Responses 的 `input[]` 拆回 `messages[]`**：

| Responses 字段 | ChatRequest 字段 | 处理 |
| ---- | ---- | ---- |
| `instructions`（string） | `messages[]` 一条 `role=system` | 系统提示词，拼进 messages |
| `input`（string） | `messages[]` 一条 `role=user` | 纯字符串入站时兜底 |
| `input[].type=message` + `role=user` 的 `content[]` | `role=user` + `content` | 拆 text/input_text |
| `input[].type=message` + `role=assistant` 的 `content` | `role=assistant` + `content` | 历史 assistant 回复回填 |
| `input[].type=message` + `role=developer` | `role=developer`（v6.1 已支持）| 对应 Chat 的 developer 角色 |
| `input[].type=function_call` | `role=assistant` 的 `tool_calls[]` | 带 `call_id`/`name`/`arguments` |
| `input[].type=function_call_output` | `role=tool` + `tool_call_id` + `content` | 工具结果回填 |
| `input[].type=input_text` | `role=user` + `content` | 纯文本 user |
| `input[].type=input_image` | `content_blocks`（image_url 块） | 多模态，转成 Chat content_blocks |
| `input[].type` 无对应（`web_search_call`/`computer_call`/`local_shell_call`/`file_search_call`） | 直接跳过 | 与 sub2api 一致，降级丢弃 |
| `tools[]`（Response tool 声明） | `tools` | 转成 Chat tools：`type=function` → function；`web_search` 等服务端工具丢弃 |
| `reasoning.effort` | `reasoning_effort` | 映射推理强度 |
| `max_output_tokens` | `max_tokens` | 映射最大 token |
| `text.format` | `stream`/`response_format` 语义 | 非流式/流式按需 |
| `stream` | `stream` | 直透 |

### 4.2b 入站转换器：Anthropic `/v1/messages` → ChatRequest 字段映射

牛码**原生支持 Anthropic 出站**（kimi 现就走 `v1/messages`），所以此入站转换的关键是把 Anthropic 请求体拆回 ChatRequest，出站直接复用现成的 `_convert_anthropic_messages`。典型差异是**系统提示词在顶层 `system` 而非 `messages[]` 内、鉴权头是 `x-api-key` 而非 Bearer**。

| Anthropic 字段 | ChatRequest 字段 | 处理 |
| ---- | ---- | ---- |
| 顶层 `system`（string 或 block 数组） | `messages[]` 一条 `role=system` | 从顶层取出，拼进 messages |
| `messages[].role=user` 的 `content`（string） | `role=user` + `content` | 纯文本 user |
| `messages[].role=user` 的 `content`（block 数组） | `content_blocks` | 拆 text / image 块 |
| `messages[].role=assistant` 的 `content` | `role=assistant` + `content` | assistant 回复回填（含 `thinking` 块 → `reasoning_content`）|
| `content` 块 `type=tool_use` | `role=assistant` 的 `tool_calls[]` | `id`/`name`/`input` → tool_calls |
| `content` 块 `type=tool_result` | `role=tool` + `tool_call_id` + `content` | 工具结果回填 |
| `content` 块 `type=thinking` | `reasoning_content` | Anthropic thinking → Chat reasoning |
| `tools[]`（Anthropic tool 声明） | `tools` | `input_schema` → Chat function.parameters |
| `max_tokens` | `max_tokens` | 直透 |
| `thinking.type` / `budget_tokens` | `thinking=True` / `reasoning_effort` | 复用现有 thinking 处理 |
| `x-api-key` 鉴权头 | 鉴权（`RELAY_API_KEY`） | 入站需兼容 `x-api-key` 提取（对标 sub2api `api_key_auth.go`）|

### 4.3 出站响应方向：牛码 SSE → 各格式

入站转换只是第一半，**响应方向要把牛码的 SSE 组装成 Responses 的 `output[]` 事件**（这是最难、也最需要对照 sub2api 的部分）：

- **非流式**：`chat_response_to_openai` 的 `choices[].message` 语义 → Responses 的 `output[]` 类型化数组：
  - `message.content` → `{type:"message", content:[{type:"output_text"}]}`
  - `message.tool_calls[]` → `{type:"function_call", call_id, name, arguments}`
  - `reasoning` → `{type:"reasoning", summary:[...]}`
  - `finish_reason=length` → `status:"incomplete"` + `incomplete_details.reason:"max_output_tokens"`
- **流式**：把现有 OpenAI SSE 分帧（`stream_openai_sse` 产出的 `chat.completion.chunk`）重排成 Responses 的事件流（`response.created` / `response.output_item.added` / `response.output_text.delta` / `response.function_call_arguments.delta` / `response.output_item.done` / `response.completed`）。
  - 参照 sub2api `backend/internal/pkg/apicompat/chatcompletions_responses_bridge.go` 的 `ChatCompletionsChunkToResponsesEvents` + `FinalizeChatCompletionsResponsesStream` 状态机。
  - 或参照 `responses_to_anthropic.go` 的 `ResponsesEventToAnthropicEvents`（若同时做 Anthropic）。

> 说明：牛码出站仍走现有 `Ta3Provider`（`stream_structured` 产出 thinking/content/tool_calls/done 事件），只改「把 provider 事件翻译成各外部协议 SSE 帧」的组装层，**不动牛码探测/鉴权/工具伪装**。

**Anthropic `/v1/messages` 响应方向**（中等难度，出站可大量复用现有 `_parse_anthropic_frame` 的逆过程）：

- 非流式：`ChatResponse` → Anthropic `{type:"message", content:[{type:"text"}, {type:"tool_use"}, {type:"thinking"}...], stop_reason}`（对照 sub2api `responses_to_anthropic.go`）。
- 流式：牛码 SSE → Anthropic typed 事件（`message_start` / `content_block_start` / `content_block_delta` / `message_delta` / `message_stop`）——**因为牛码 kimi 本来就走 Anthropic SSE，此响应转发几乎是同构透传**，成本最低。

### 4.4 端点注册与鉴权

- 新增两个入口（`relay/relay/routes.py`），与现有 `/v1/chat/completions` 并列：
  - `@app.post("/v1/responses")`
  - `@app.post("/v1/messages")`
- **鉴权**：统一走 `RELAY_API_KEY`。三种入站兼容提取不同鉴权头：
  - Chat Completions / Responses：`Authorization: Bearer`（现有逻辑，无需改）
  - Anthropic `/v1/messages`：客户端用 `x-api-key`（**非 Bearer**），需在鉴权中间件兼容提取（对标 sub2api `api_key_auth.go` 的 `Bearer`/`x-api-key`/`x-goog-api-key` 三头统一）。
- **可选**：为了让「习惯不写 /v1」的 agent 也能连，可同时注册无 `/v1` 前缀的别名路径（`/responses`、`/messages`），与 sub2api 的别名（`/backend-api/codex/responses` 等）一致。

## 5. ChatRequest 可靠性质疑（k3 自动结束）

### 5.1 反馈

用户称：参考实现 后端由 AI 生成、同事亦不懂 agent 开发；用 kimi-k3 时「任务没做完就自动结束，只能反复发继续」。

### 5.2 初步判断（待复现确认）

`ChatRequest` 本身是 Pydantic 字段容器（`relay/app/models/schemas.py`），仅存 `messages/model/tools/max_tokens/thinking` 等字段，**无任何执行逻辑**，不大可能直接导致「中途结束」。真正可疑的是**用这些字段组装请求/解析响应的适配层**：

| 候选根因 | 代码位置 | 表现 |
| ---- | ---- | ---- |
| `max_tokens` 受限 | `ta3.py::_build_anthropic_body`（kimi 上限 32768） | agent 传的 max_tokens 小则写满即 `length` 结束 |
| kimi thinking 回传缺失 | `ta3.py::_convert_anthropic_messages`（v29 已修） | 旧版或历史 messages thinking 缺失 → 网关异常解析 |
| Anthropic SSE 提前 terminal | `ta3.py::_parse_anthropic_frame` | `message_delta.stop_reason` 提前触发误判完成 |
| 出站协议切换 | `ta3.py::_stream_llm` | kimi 走 `v1/messages`，上流断流/空响应 |

### 5.3 待复现确认的日志字段（拿日志定位，勿臆断）

复现 k3 自动结束时，请记录 CoderProxy 日志面板的以下字段：

1. `finish_reason`：是 `stop` / `length` / `max_tokens` / `tool_use` / `thinking_timeout`？
2. 思考看门狗超时警告（`thinking_timeout` / `思考看门狗`）
3. 空响应流警告（`无 content/thinking/tool_calls, finish=stop`）
4. 请求里 `max_tokens` 值（对照 kimi 目录上限 32768）
5. `model` 名是否 kimi-k3、出站 `protocol=anthropic`

### 5.4 处置原则

- 在拿到日志前，**不臆断是 `ChatRequest` 结构问题，不重写 参考实现 后端**。
- 若日志显示 `max_tokens` 限制 → 属配置问题（改配置）。
- 若显示 thinking 回传缺失 / 空响应 → 改 `ta3.py` 适配层。
- 若显示 SSE 提前终止 → 改 `_parse_anthropic_frame`。
- **仅当上述适配层均排掉后**，才考虑 `ChatRequest` / vendored 后端本身的问题。

## 6. 已知边界

- 三协议「互转」可行，但 Responses 的专有内置工具（`web_search_call` / `computer_call` / `local_shell_call` / `file_search_call`）降级到 Chat/Anthropic 时**无对应字段，会丢弃**；对 Codex CLI 影响小（其主用 function calling）。
- 入站自动识别（方案 A）需区分 Anthropic 顶层 `system` 与 Chat 的 `messages[].system`。
- 对外鉴权头三种不一（Bearer / x-api-key / x-goog-api-key），入站鉴权需兼容提取（对标 sub2api `api_key_auth.go`）。
