## 1. 背景与目标

当前 CoderProxy 的监控数据是**内存态**的：

- 日志事件存在于 [monitor.py](../../../relay/relay/monitor.py) 的环形缓冲（默认 500 条，重启即丢），无分页与筛选；

- token（prompt/completion/cached/reasoning/total）虽已能从上游解析，但**未落盘**；

- 需求：日志可持久化、跨重启保留、支持分页与多条件筛选，并为 M7 的 token 统计提供同源数据底座。

### 目标

1. 引入轻量 SQLite（标准库 `sqlite3`）持久化日志，跨重启保留。
2. 每次 chat 请求落库：类型 / 模型 / 是否流式 / 各 token 数 / 耗时。
3. 提供 `/v1/logs` 分页 + 多条件筛选（时间 / 模型 / 类型）；筛选字段可扩展。
4. 提供 `/v1/logs/kinds`、`/v1/logs/models` 供筛选项下拉。
5. 事件循环不被写库阻塞。

### 非目标

- 本里程碑**不做** token 聚合统计页（归 M7）。

- **不记录消息正文**（仅元信息），避免隐私负担与库体膨胀。

- 配置类数据（api\_key / 白名单 / 端口）继续用原 JSON 存储，**不迁移**。

## 2. 设计方案

### 2.1 选型：标准库 sqlite3（已拍板）

- 零第三方依赖，PyInstaller 打包 sidecar 无需新增 hiddenimports；

- 单文件数据库，落 `data_dir/coderproxy.db`，随应用数据目录走（打包态正常）；

- 启用 WAL 提高并发读写。

**被否决的备选**

- `aiosqlite`：异步驱动更优雅，但引入依赖、需配置 PyInstaller hiddenimports，量级上收益有限。

- 继续内存 ring buffer：满足不了持久化/分页/筛选。

### 2.2 存储层 `relay/relay/db.py`（新建）

```
data_dir/coderproxy.db  (WAL)
└─ logs
   ├─ id            INTEGER PK AUTOINCREMENT
   ├─ ts            TEXT        -- UTC ISO8601（毫秒），索引
   ├─ kind          TEXT        -- chat_request / chat_done / chat_error / auth_401_refresh ...
   ├─ model         TEXT
   ├─ stream        INTEGER     -- 0/1
   ├─ prompt_tokens / completion_tokens / cached_tokens / reasoning_tokens / total_tokens INTEGER
   ├─ duration_ms   INTEGER     -- chat_done 时由耗时换算
   └─ detail        TEXT        -- JSON 占位（如 error 摘要），预留扩展
```

**扩展策略：独立列为正、JSON 兜底为副（已拍板）**

- 主字段都建为**独立列**（type/ts/kind/model/tokens/...），带类型、可索引，承担检索/筛选/聚合——`detail` JSON 不参与任何 WHERE/GROUP BY，只作「明确不建列」时的兜底口袋（如 error 摘要、嵌套快照）。

- **schema 自省自动补列**：启动时 `PRAGMA table_info(logs)` 对比声明的列清单，缺什么就 `ALTER TABLE ... ADD COLUMN` 补齐。以后加扩展字段只需改 schema 清单，旧库自动升列，**不需手跑 SQL**。

- `ADD COLUMN` 约束：新列必须**可空**（或带默认值）；不得是 NOT NULL / PRIMARY KEY / UNIQUE。因此扩展列一律设计成可空——旧数据该列为 `NULL`，前端显示 `-` 或留白即可，符合预期。

接口（异步封装，防阻塞）：

- `log_event(**fields)`：插入一条日志。

- `query_logs(limit, offset, kind=None, model=None, time_from=None, time_to=None) -> (rows, total)`。

- `distinct_kinds()`、`distinct_models()`。

- `clear_logs(kind/model/time...)`：清空（支持按条件）。

- `prune(max_rows=100000)`：超上限滚动删除最旧（保留策略）。

- 内部用**单写线程 + asyncio queue** 或 `asyncio.to_thread` 避免阻塞事件循环；线程锁保护 sqlite 连接。

> `settings` 已有 `data_dir`；连接初始化放 `ensure_initialized` 或首次用时 lazy 建库。

### 2.3 落库点扩展（`relay/relay/routes.py` + `oai_adapter.py`）

**落库 kinds 白名单**（对齐 monitor 现有 emit 点，各点做「落库为并行旁路」）：

| kind               | 触发点                     | 落库内容                         |
| ------------------ | ----------------------- | ---------------------------- |
| `chat_request`     | `chat_completions` 收到请求 | model / stream / tools 数     |
| `chat_done`        | 流式 done 或非流式返回          | duration\_ms + usage 各 token |
| `chat_error`       | 流式/非流式异常                | error 摘要（detail，截断 500 字符）   |
| `auth_401_refresh` | 上游 401 刷新重试             | model                        |

> `tool_disguise` 不单独落库（与 chat\_request 同点、仅工具映射计数，且不入统计口径）；monitor 的其它事件同理。未来如需审计可按下述 schema 自省补列策略扩展独立列。

**duration\_ms 口径（定稿）**

- 起点：`chat_completions` 收到请求时刻（`time.monotonic()`，与 chat\_request 落库 ts 同源）；

- 终点（流式）：provider 的 done 事件到达（上游完成，含工具调用解析），**不含** SSE 下行至 agent 的耗时；

- 终点（非流式）：`_chat_with_retry` 返回 `ChatResponse`。

- 存整数毫秒。

**usage 来源与字段映射（定稿）**

vendored provider 的 done 事件**总是**携带 `usage: Usage`（无关 agent 是否传 `include_usage`；上游没给 usage 时 vendor 兜底为全 0 的 `Usage()`）。字段映射：

| logs 列             | 来源                                                             |
| ------------------ | -------------------------------------------------------------- |
| prompt\_tokens     | `Usage.prompt_tokens`                                          |
| completion\_tokens | `Usage.completion_tokens`                                      |
| cached\_tokens     | `Usage.cached_input_tokens`（vendor 已把上游 `cached_tokens` 并入此字段） |
| reasoning\_tokens  | `Usage.reasoning_tokens`                                       |
| total\_tokens      | `Usage.total_tokens`                                           |
| duration\_ms       | §2.3 duration 口径                                               |

**流式 usage 必须打通传出通道（现网缺口，核心改造点）**

现状核对：`oai_adapter.stream_openai_sse` 内部能拿到 done 事件的 usage，但仅在 `include_usage=True` 时转成 SSE 帧发给 agent、否则丢弃；且它是 async generator，`routes._sse_with_retry` 只 yield 帧不返回值 → **routes 层拿不到流式 usage**。文档上一版「在 \_sse\_with\_retry 完成后的 chat\_done 处已可取得」的前提不成立，本版给出明确改造：

1. `oai_adapter.stream_openai_sse(provider, request, include_usage, usage_sink=None)`：新增可选 `usage_sink: list[Usage]`；收到 done 事件时 `usage_sink.append(event["usage"] or Usage())`。
2. `routes._sse_with_retry(..., usage_sink=None)` 透传该参数。
3. `chat_completions` 的流式 `gen()`：进入时建空 `sink`；`_sse_with_retry` 正常结束后取 `sink[-1]` 作为本次 usage 落库。401 重试语义：每次 attempt 重新置空 sink，成功后取最后一次值——天然取到成功那次（失败 attempt 的 usage 忽略）。
4. 非流式：`_chat_with_retry` 返回的 `ChatResponse.usage` 直接可用（**修正上一版措辞**：不需要等 `chat_response_to_openai` 的结果再反解析）。
5. 约束：改动仅限 `relay/relay/` 下代码（oai\_adapter.py / routes.py），**不改 vendored** **`app/`**（AGENTS 硬性规则 1）。

**被否决的备选**

- 在 `gen()` 里自行解析 SSE 帧中的 usage：`include_usage=False` 时无 usage 帧 → 拿不到，否决。

- contextvar / 全局变量传 usage：并发请求互相串扰，否决。

- 改 vendored ta3.py 的 done 事件结构：违反硬性规则 1，否决。

### 2.4 查询 API（`routes.py`）

- `GET /v1/logs`：参数 `limit`(默认50,max200) / `offset` / `kind` / `model` / `time_from` / `time_to`（UTC ISO）。
  返回 `{ rows: [...], total, kinds: [...], models: [...] }`。筛选用查询参数动态拼接 SQL 条件，新增筛选项零成本。

- `GET /v1/logs/kinds` / `GET /v1/logs/models`：distinct 列表，供前端下拉。

- `DELETE /v1/logs`：按可选 `kind/model/time` 条件清空（无参数=全清）。

### 2.5 保留策略

- 默认保留最近 `100000` 行，插入后 `prune` 滚动删除最旧。

- 上限做成常量/可配（`config.RELAY_LOG_MAX_ROWS`），避免磁盘无限膨胀。

### 2.6 数据目录共享指针底座（壳侧，本期实现，无 GUI）

**背景**：上一版规则「便携版绑定 exe 旁 `data/`、安装版回退 AppData」导致多版本登录态 / 白名单 / 端口 / 日志互不共享。用户拍板改为**共享模式**：

> AppData 目录（`app_data_dir`）只保存一个东西：**指针文件**，内容是「真实软件数据目录」的绝对路径。任意版本（便携 / 安装）启动都先读该指针 → 命中同一真实数据目录 → 登录态、模型白名单、端口、日志、token 统计全部共享。

**规则设计（M6 本期在 Rust 壳落地）**

1. **指针文件**：`<app_data_dir>/data_path.txt`，UTF-8 纯文本，内容为真实数据目录绝对路径；更新用「写 tmp + rename」保证原子（本期只写不「改」，改归 M10）。
2. **默认真实数据目录**：`<app_data_dir>/data`（即 AppData 子目录）。此时物理上 AppData 内是「1 个指针文件 + 1 个数据子目录」；用户通过设置页（M10）改到其它位置后，AppData 内只剩指针文件这一配置物。
3. **解析顺序（改写 Rust** **`resolve_data_dir`，本期实现）**：

   - 指针文件存在 → 校验所指目录可写 / 可建；可用则返回它（所有版本共享）；

   - 不存在（首次启动）→ 用默认 `app_data_dir/data`，创建并写入指针文件；

   - 废弃「exe 旁 `data/` 优先」的旧规则。
4. **旧数据一次性迁移**：若 `app_data_dir/relay_state.json` 存在（旧版遗留）而指针目标目录没有 → 复制一次进真实数据目录；后续版本数据均在指针目录，不再有「从 AppData 迁出」的场景。
5. **db 无感**：Rust 侧把真实数据目录经 `RELAY_DATA_DIR` env 传给 sidecar（现有链路不变），Python 侧 `settings.data_dir` / `coderproxy.db` 自然落在共享目录，**零改动**。
6. **并发 / 双开风险（写进边界）**：共享 ≠ 可并行双开。两个 relay 同时读写同一 `relay_state.json`（storage 的锁是进程内的，不跨进程）可能损坏；且共享端口配置会撞端口。**同一台机器同一时刻只运行一个 CoderProxy 实例**；sqlite WAL 本身多进程安全，但双开整体不支持。
7. **指针失效策略（本期随底座定稿）**：启动时指针指向的目录不可访问 / 不可写 → GUI 提示「数据目录不可访问：<path>」并提供重选入口；期间以隔离默认目录（`app_data_dir/data`）起服避免不可用。重选 = M10 的改目录流程。M10 §2.3 与此条口径一致。

**设置页（改目录 + 迁移 + UI）不在本期**：M6 只做只读底座（解析 + 默认目录 + 首次写指针）；「查看 / 修改数据位置」已拆为独立需求 **M10-设置页与侧边栏登录**，在底座上直接扩展。

## 4. 验收（实现前必填）

1. 冷启动后建库；连续发起 chat（流式+非流式）后 `/v1/logs` 返回行数正确，含 `usage` token 与 `duration_ms`。
2. 重启 relay 后日志仍在（落 SQLite 非内存）。
3. 分页：`limit/offset` 正确，`total` 正确。
4. 筛选：按 模型 / 类型 / 时间区间 各自正确且可组合。
5. `chat_error` 能落库（异常路径覆盖）。
6. `DELETE /v1/logs`（含条件清空）生效。
7. 事件循环无阻塞（写库走后台），并发/长时间下有监控事件不丢、不卡请求。
8. PyInstaller 打包 sidecar 后 SQLite 可正常建库读写（标准库，无需 hiddenimports）。
9. relay 单测新增覆盖：建库、插入、查询筛选分页、清空、prune。
10. **schema 自省补列**：旧库（缺某列）启动后自动 `ADD COLUMN` 补齐，旧行该列为 `NULL`，新写入正常。
11. **流式 usage 落库（含** **`include_usage=false`）**：流式请求不传 `stream_options` 时，logs 的 chat\_done 行各 token 仍与上游一致（非全 0，除非上游确实没返回）；401 重试成功时取重试那次 usage。
12. `coderproxy.db` 建在 `settings.data_dir`（即共享指针目录），随 `RELAY_DATA_DIR` 走，Python 侧无额外路径处理。
13. **指针底座（壳侧）**：首次启动在 `app_data_dir` 写入 `data_path.txt`（内容 = 默认 `app_data_dir/data`），`relay_state.json` 与 `coderproxy.db` 均落在该目录。
14. **共享命中（壳侧）**：第二份 exe（便携 / 安装 / 其它目录）启动读同一指针命中同一数据目录；同一时刻仅单实例（§2.6 规则 6）。
15. **旧数据迁移（壳侧）**：旧版遗留 `app_data_dir/relay_state.json` 一次性复制进数据目录，登录态不丢；指针失效时按 §2.6 规则 7 提示与降级起服。
