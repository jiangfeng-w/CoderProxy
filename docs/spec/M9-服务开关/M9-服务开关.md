# M9 对 agent 的 /v1 服务开关（软停，不动底座）

> 状态：已实现（2026-09-04）
> 优先级：交付
> 来源：用户明确「服务 = `http://127.0.0.1:<port>/v1` 这个给 agent 用的 base-url，不是整个软件底座」。此前「停止/重启服务」在 Rust 侧 kill/spawn 整个 relay 进程，会把登录/配置/日志一起停；本期改为只开关 /v1 对外服务
> 依赖：M4 Tauri 壳 / M6 数据底座（relay 单进程同时承担底座与 base-url）
> 定稿日期：2026-09-04

## 1. 背景与目标

relay 是**同一个 FastAPI 进程**，同时承担两类职责：

- **底座 / 控制面**：`/v1/auth/*`（登录、状态、配置）、`/v1/logs`、`/v1/stats`、`/v1/monitor/*`

- **给 agent 的 base-url**：`/v1/chat/completions`、`/v1/models`

此前顶栏「停止服务 / 重启服务」直接对整进程 kill / spawn（[lib.rs](../../../src-tauri/src/lib.rs) [`relay_stop`/`relay_restart`](../../../src-tauri/src/lib.rs)），所以「停 base-url」会连带登录、配置、日志一起停。本期把「对 agent 的 /v1 服务」做成**可独立开关的逻辑门控**：relay 进程常驻，只关/开 /v1 对外服务。

### 目标

| #  | 功能        | 说明                                                                                                 |
| -- | --------- | -------------------------------------------------------------------------------------------------- |
| F1 | 服务可独立停    | `/v1/chat/completions` 与 `/v1/models`（agent 视角）在停止时返回 503；`/v1/auth/*`、`/v1/logs`、`/v1/stats` 不受影响 |
| F2 | 登录后自动启动   | 服务可用 = 已登录 且 未手动停止；未登录时 /v1 默认 503                                                                 |
| F3 | 手动停止 / 启用 | 顶栏「停止服务」= disable；「重启服务」= enable（进程异常退出时可回退为真实重启）                                                  |
| F4 | 登出复位      | 登出后服务开关复位，下次登录自动启动                                                                                 |
| F5 | 底座不受影响    | 停 base-url 不动登录 / 配置 / 日志进程                                                                        |

### 非目标

- ❌ 停 base-url 时**真正释放端口**：当前保留进程、仅返回 503。真正关端口需把底座与 base-url 拆成**两个进程 / 两个监听端点**（架构级拆分，本期不做）。

- ❌ 改造「保存端口后自动重启」：监听端口是进程级绑定，改端口**必须**整服务重启，此为合理行为（归 M4/M6 既有逻辑）。

## 2. 设计方案

### 2.1 relay 侧（[routes.py](../../../relay/relay/routes.py)）

- 模块级 `_service_disabled: bool`（进程级运行时状态，**不持久化**；进程重启自动复位为 False）。

- `async def _serving() -> bool`：`not _service_disabled and login_status == "logged_in"`。

- 门控：

  - `POST /v1/chat/completions` → 非 serving → `503 服务已停止，请登录并启动服务`。

  - `GET /v1/models`（`all` 缺省/`0`，agent 视角）→ 非 serving → `503`；`?all=1`（GUI 管理用）不受影响。

- 新增接口：

  - `GET /v1/service` → `{enabled: bool}`。

  - `POST /v1/service/disable` → 置 `_service_disabled=True`，返回 `{enabled:false, status:"stopped"}`。

  - `POST /v1/service/enable` → 置 False，返回 `{enabled: <serving>, status:"started"}`（需已登录才真正为 True）。

- `POST /v1/auth/logout` 末尾复位 `_service_disabled=False`（登出复位，下次登录自动启动）。

### 2.2 前端（[Shell.vue](../../../frontend/src/Shell.vue) / [api.ts](../../../frontend/src/api.ts) / [store.ts](../../../frontend/src/store.ts)）

- `store.serviceEnabled` 由 `GET /v1/service` 轮询填充；`serviceRunning = relay.running && serviceEnabled`。

- 顶栏状态文案：`运行中 / 已停止 / 登录中·登录后自动启动服务 / 未登录·登录后自动启动服务`。

- 顶栏「停止服务」→ `serviceDisable`；「重启服务」→ `serviceEnable`，失败回退 `relayRestart`（硬重启兜底）。

### 2.3 Rust（未改动）

- relay 进程照常 `spawn`，停止仅为 relay 内开关，不 kill 进程。

- `relay_stop` / `relay_restart` 命令仍保留；`relay_restart` 供配置页改端口使用。

## 3. 已知边界

- 停 base-url 是**逻辑 503**，端口仍监听；要真正关端口需拆分进程（见非目标）。

- 手动停止后，GUI「模型页 - 测试」同样会 503（与 agent 视角语义一致）。

- keyless 单测默认模拟「已登录 + 服务开」基准（测试 fixture 顶替 `_serving`），聚焦后端逻辑本身。

## 4. 验收

1. 未登录：`GET /v1/service` → `enabled=false`；`/v1/chat/completions`、`/v1/models`（默认）→ 503。
2. 登录后：`enabled=true`；`/v1/models`（默认）可用；`?all=1` 始终 200。
3. 手动停：`enabled=false`，agent 入口 503；`/v1/auth/*`、`/v1/logs`、`/v1/stats` 仍 200。
4. 重新启用：`enabled=true`，`/v1/models`（默认）恢复 200。
5. 登出：`_service_disabled` 复位为 False。
6. 前端 `npm run build` 通过；relay `py -3.13 run_tests.py` 全绿（含新增 `test_service_gate.py`）。
