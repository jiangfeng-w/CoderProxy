# 连通性测试白名单豁免

> 状态：开发中
> 优先级：核心（GUI 模型页可操作性缺陷；不影响 agent 对已启用模型的日常转发，可排队）
> 来源：2026-09-04 排查「模型 deepseek-v4-flash-vision-exp 连通性测试报 404 未知或未启用的模型」。现场数据：已登录、目录已同步（本地 models 缓存含 5 个模型）、白名单 `['kimi-k3','deepseek-v4-flash']`；日志（14:48-14:50 UTC）显示白名单内模型测试 `chat_done`、白名单外模型一律 404。定位结论：404 由 relay 本地 `_ensure_model` 主动抛出（[routes.py](../../../relay/relay/routes.py)），请求**从未到达牛码上游**，非 `lc.yinhaiyun.com/newcoder` 返回。
> 依赖：M4 白名单底座（storage.is\_model\_enabled / relay 侧 404 口径）；GUI 模型页交互（Models.vue / modelCheck.ts，实现期长出、无对应 spec）
> 定稿日期：2026-09-04（方案 A + body probe 标记法）

## 1. 背景与目标

### 背景：白名单 404 与「先测后启用」的交互死锁

M4 spec 明文「chat 对白名单外模型 404」（[M4 验收](../../../docs/spec/M4-Tauri桌面壳与GUI/M4-Tauri桌面壳与GUI.md)），relay 实现无任何豁免：`/v1/chat/completions` 一律经 [\_ensure\_model](../../../relay/relay/routes.py) 校验白名单，白名单外抛 404。该约束对 GUI 请求与 agent 请求一视同仁。

而模型页 GUI（Models.vue / modelCheck.ts）在实现期自行长出了与 spec 无冲突记录、但与此约束**互相矛盾**的交互：

- 「启用开关」= **先测连通性，测通才写入白名单**，失败保持关闭（[Models.vue onToggle](../../../frontend/src/views/Models.vue)）；

- 连通性测试走的是普通 `POST /v1/chat/completions`（[modelCheck.ts testModel](../../../frontend/src/modelCheck.ts)）。

两者求交集的后果：对**当前未启用**的模型，测试请求在 relay 本地就被白名单 404，永远到不了牛码上游 → 测试必然失败 → 永不写入白名单 → **该模型永远无法经「启用开关」被启用**，死锁。绕过途径只剩「全部启用」（清空白名单为 `[]`）或手改白名单。默认「白名单为空 = 全部启用」的 happy path 无此问题，故 M4–M9 验收与冒烟均未暴露；「测试/启用」交互亦无任何 spec 里程碑设计过（仅 M9 spec 作为既有功能引用一次），属**实现先于文档且未回填**。

附带发现（同批优化候选）：404 文案「请先登录并同步模型目录」在「已登录且目录已含该模型、仅被白名单过滤」的场景下是误导性提示；且「请到配置页启用」中的配置页实际为「模型页」（M10 设置页规划中，白名单开关在模型页）。本需求不强制处理，建议随本次一并校准或单独立项。

### 目标

| #  | 功能       | 说明                                                     |
| -- | -------- | ------------------------------------------------------ |
| F1 | 测试请求真到上游 | 「测试/启用」流程对**未启用**模型也能把请求真实转发到牛码，返回真实可用性结论              |
| F2 | 白名单约束不破  | agent 对白名单外模型的正常 `/v1/chat/completions` 请求仍 404（行为不回退） |
| F3 | 交互闭环     | 「启用开关」「测试」「同步后批量测试」三者对已登录场景全部可用，结论与上游真实可用性一致           |
| F4 | 门控不降级    | 测试通道仍受「已登录 + 服务开关 + api-key」约束；不引入对 agent 无鉴权的旁路       |

### 非目标

- ❌ 不改变 agent 对白名单外模型的正常请求语义（仍 404）。

- ❌ 不新增上游模型可用性判断逻辑（只保证测试请求能到达上游）。

- ❌ 不改 vendored `relay/app/**`（AGENTS 硬性规则 1）；改动面限自研 `relay/relay/*` 与 `frontend/src/*`。

- ❌ 不拆进程 / 不新增常驻服务 / 不动 `/v1/models?all=1` 语义。

## 2. 设计方案（定稿：方案 A + body 标记法）

### 方案 A：服务端「探针」豁免（管理通道语义固化到协议层）

**思路**：GUI 测试请求携带管理标记，relay 对标记请求**跳过白名单校验但照常真实转发**；agent 普通请求无标记、行为不变。

要点：

- 标记形式（定稿）：**`POST /v1/chat/completions` body 加 `probe: true` 内部字段**；relay 读取该标记后不进入 ChatRequest，**绝不转发给上游**。不采用独立端点 ②（与普通请求同构性最差、多维护一个入口）。
- relay 在 `_ensure_model` 白名单判定前分叉：`probe=true` → 跳过 `storage.is_model_enabled`（仍要求模型存在于目录，不存在仍需 404 并提示同步）；其余照旧。
- 门控不变：`_serving()`（登录 + 服务开关）与 `require_api_key` 在 probe 上同样生效。
- 日志照常落 `chat_request / chat_done / chat_error`（测试本就计入监控/统计，现状即如此）。

**优点**：语义最干净——「测试 = 真实转发」由协议保证，不依赖 GUI 时序；已启用模型测试路径零变化；后端改动集中（一条分支 + 字段剥离）。

**代价 / 争议**：

- `probe` 仅靠「约定」区分，懂内部协议的调用者可借其绕过白名单——接受：白名单是 **UX 软约束（防 agent 误选）而非安全边界**，绕过者仍需合法 api-key + 登录，风险与正常聊天同级。
- 需后端单测覆盖「probe 请求不把标记转发给上游、白名单外 probe 仍转发」。
- 若采用独立端点 ②，仍需确认与 `/v1/models/{id}`（GET 目录查询）不冲突。

**风控硬约束（定稿前置，红线）**：probe 的真实转发**必须与普通聊天请求完全同构**，禁止为 probe 另写裸请求路径——上游请求只经 `Ta3Provider._stream_llm` 发出（[ta3.py](../../../relay/app/models/providers/ta3.py)），probe 同样走 `build_provider` + `Ta3Provider.chat`，从而原样继承全部伪装要素：

- 请求指纹：Electron 同族 UA / `X-Call-Source: APP` / `api-key`·`x-api-key`+`anthropic-version` / 目录条目 `requestHeaders` / temperature·thinking·prune 等体指纹；
- 上游鉴权：**目录条目自带的 `llm- key`**（非账号 OAuth token，条目同步自上游 assistant 配置）；
- 门控：`_serving()`（已登录 + 服务未停）与 `require_api_key` 对 probe 同样生效，未登录/停服与普通请求一致拒绝；
- 标记剥离：`probe` 标记在构造 ChatRequest 前消费（`oai_adapter.oai_request_to_chat_request` 系手写挑字段，未知字段天然不入模型/上游 body），任何情况下不得出现在转发给上游的 JSON 中；
- 工具伪装：机制与普通请求同一 provider 同一 `DisguiseContext`；probe 无 tools 即无实际作用面，有 tools 也必须走同一映射，不得绕过。
- 频率边界：probe 保持现有 testModel 的极小消息形态（单条 user `Hi!`、无 tools）；批量测试沿用现有**顺序串行**与「登录后每会话一次」约束（上游有并发/频控，见 modelCheck.ts / store.ts）；冒烟只用小号（AGENTS 硬性规则 5）。方案 A 只放开「可测模型范围」，不放大频率、不新增并发。

### 方案 B：前端「临时启用 → 真测 → 固化/回滚」（relay 零改动）

**思路**：GUI 在测试前先把目标模型临时加入白名单（`onToggle` / `onTest` / `batchTestAll` 统一），测试成功→固化，失败→移除；`batchTestAll` 在「部分启用」态下先临时放开全表再按结果重建白名单。

**优点**：relay 完全不改，风险集中在前端，测试请求天然到达上游。

**代价 / 争议**：

- 测试瞬间模型短暂对 agent 可见（白名单是软约束、影响小，但需接受并知会）。

- 「手动测试」按钮语义从「失败自动关闭」变为「会短暂放行再按结果固化/回滚」，需 GUI 文案与状态提示配合，否则用户困惑。

- 「白名单为空 = 全启用」与「非空」两模式的读写逻辑需重推演，避免把 `[]` 误写成超长排除列表（现 onToggle 已有此隐患分支）。

- 死锁虽解，但「测试要改白名单时序」仍隐式依赖前端每一步都走对；若未来出现第三个调用测试通道的入口，易漏。

### 方案 C（否决）

「chat 不再做白名单过滤，仅 /v1/models 过滤」——直接破坏 M4 验收口径「chat 对白名单外模型 404」，且让 agent 可选模型与可调用模型不一致，否决。

> **定稿结论（2026-09-04）**：方案 A + body `probe: true` 标记法。理由：把「测试请求应到达上游」固化到 relay 协议层，语义单一、不依赖 GUI 时序；与普通请求**同一入口**天然保证伪装同构（见上文风控硬约束）。方案 B 不采用（留档：零后端改动的降级备选）。probe 标记剥离由 `oai_adapter.oai_request_to_chat_request` 手写挑字段天然保证（未知字段不入 ChatRequest / 上游 body）。

### 实现明细（2026-09-04）

- 后端：`_ensure_model(model_name, probe=False)` 在 `probe=True` 时跳过白名单启用判定（仍校验目录存在性，不存在 404 并提示同步）；`chat_completions` 读取 body `probe` 仅本地消费（不进 ChatRequest / 上游 body）；`_sse_with_retry` / `_chat_with_retry` 透传。relay 单测全量通过（新增 `tests/test_model_probe.py` 5 条）。
- 前端：`modelCheck.testModel` 统一携带 `probe: true`（启用开关 / 手动测试 / 登录与同步后批量测试共用同一探测入口）。
- GUI 交互收敛（消除启用开关与「测试」按钮的功能重复）：**启用开关改为纯白名单成员管理、不再内嵌连通性预检**（即时生效）；**测试与启用开关完全解耦**——测试（手动/批量）只更新连通状态、不修改白名单，失败不摘除已启用模型；白名单只由开关与「全部启用/禁用」控制。
- 模型页状态列收敛为「连通状态」四态：**未测试 / 测试中 / 成功 / 失败**（store.modelStatus 键 success/failure/testing，无记录=未测试）；**启用与否不参与状态列**（由右侧白名单开关表达，两者解耦）。「成功但未启用」时行内显示弱引导「未启用 · 点击启用」，点击直接写入白名单（纯展示 + 弱引导，无新状态）。
- 「同步模型」按钮只**拉取最新目录 + 刷新 GUI 列表，不再自动批量连通性测试**（测试收敛为显式动作）；登录后**每会话一次**的自动摸底保留（概览页，`store.batchTested` 防重复），避免模型页常态全灰。
- 打包：PyInstaller sidecar + NSIS 安装包已产出，待真机验证。

### 实现补充（2026-09-05）

- **修复流式请求白名单外模型的 404 呈现**（commit `0a38972`）：流式 `/v1/chat/completions` 的模型/白名单校验原在 `StreamingResponse` 头（200）发出后、于 SSE 流内首迭代才执行，白名单外模型表现为「开流即断」——agent 端只见 `Stream error … Transport error … (4028)` 断流错误，无法识别真实原因。现校验提前到 SSE 建立前，未启用模型直接以标准 HTTP 404 + `{"detail":"未知或未启用的模型: …"}` 返回给调用方（与既有非流式路径行为一致）。
- 回归测试：`tests/test_model_probe.py` 新增 stream + 白名单外 → 404 JSON 用例；`tests/test_m6_logs.py` 原 mock 转发层用例因不再覆盖前置校验而补目录模型适配。relay 全量单测 101 passed。
- 真机验证（2026-09-05，GUI 安装包）：probe 对未启用模型真实到达上游、启用开关即时生效、测试与白名单完全解耦（失败不摘除）、「同步模型」不自动批量测试、状态胶囊即测试按钮四态 + 弱引导、流式前置 404 均通过。
- **小号端到端冒烟（验收项 6）**：已按 AGENTS 硬性规则 5 完成，状态翻转为「已实现」（2026-09-05 项目方确认完成）。

## 3. 已知边界 / 风险

- **probe 是软约束通道**：可被持有合法 api-key 的调用者用于绕过白名单——接受（非安全边界，见方案 A）；不把该通道视作可对外承诺的安全特性。

- **测试计入监控/统计/token**：与现状一致，不因本需求放大；冒烟遵守 AGENTS「只用小号、不反复触发」。

- **「白名单为空 = 全部启用」路径不回退**：本需求只补「部分启用」下的缺口，验收须回归两种模式。

- **文案误导（附带项）**：404 detail「请先登录并同步模型目录」在已登录场景误导；「配置页」实为模型页。建议同批校准或另行立项，本需求默认不阻塞。

- 若改后端，需重建 PyInstaller sidecar + `tauri build` 才能进 GUI 生效（开发态直跑不受影响）。

## 4. 验收

1. 「部分启用」态（白名单非空）：对未启用模型点「测试」→ 请求真实到达牛码（落 `chat_done`、含 duration/token），模型可用则返回成功。
2. 「启用开关」即时生效（不再内嵌连通性测试）：打开即写入白名单、关闭即移除；「测试」按钮与开关完全解耦——测试失败只把状态置「失败」，不修改白名单、不摘除已启用模型。
3. agent 对白名单外模型的普通请求仍 404（F2 不回退）。
4. 服务停止 / 未登录时，probe 请求同样被门控拒绝（503/未登录语义，与普通请求一致）。
5. **无裸路径回归断言**：probe 走 `build_provider` + `Ta3Provider` 同构链路（评审无独立上游请求代码）；单测断言 probe 与同模型普通请求构造的上游 URL / headers（UA、X-Call-Source、鉴权头、requestHeaders）/ body 指纹一致，`probe` 标记不出现在上游 body，无标记请求行为不变。
6. relay 单测（probe 剥离、白名单外 probe 转发）+ `vue-tsc`/前端 build + 小号冒烟一条通过。
